### 3. How to develop (the routine, one story at a time per worktree)
1. `cd workspace/sandbox`, `git fetch`, `git worktree add C:\Users\rupen\dhanya-wt\<name> -b feat/<name> origin/main`, `npm ci` in it. The `sandbox` folder itself stays on `main`.
2. Write the spec reading from the plan files. TESTS FIRST, and the FEWEST that prove each requirement (Test economy): unit tests for logic, one integration test per database rule or permission, one browser journey per flow, axe in light mode only. Money is integer paise, percentages basis points, India (IST) days, English only (Telugu is skipped: `te.json` holds the same English text), UI uses the existing components in `src/components/ui` and the Apple-style design rules. Every new API route uses `defineRoute` plus a permission-matrix row and a route-registry entry; every change writes an audit row in the SAME transaction; two sides (mill and shop) are never mixed; tenancy checks on every query.
3. Local checks only through the private runner (no port edits): `node ai-tools/check-local-docker.mjs --worktree <path> --integration <file> --browser <spec>`; also `npx tsc --noEmit`, `npm run check`, `npm run test:unit`. Commit normally (hooks run lint and types; NEVER `--no-verify`, never skip hooks, never force-push, never delete branches, never push to `main`).
4. Database changes: next migration number is 0021 (last is 0020, journal `when` 1794900000000). Merge stories in migration-number order; after merging main into a branch, the journal must be in order with increasing `when`, every `meta/NNNN_snapshot.json` must have `prevId` = the previous snapshot's id and contain EVERY table, and `npx drizzle-kit generate` must report "No schema changes" (it numbers by position and can overwrite a snapshot: check `git status`). The shared integration database on port 5433 is not for parallel builders.
5. Write `docs/plan/handoffs/<story>.md` (one page: Done, How it is built, Key files, Reuse this, Gotchas, Left for later, Numbers) and a row in that folder's README; update `decisions.md` (owner questions in plain words), `sprint-status.yaml` and `review-backlog.md`.
6. RELEASES: batch 3 to 4 finished stories into ONE release branch (merge story branches in migration order, fix journal/snapshots once), open ONE pull request titled in Conventional Commits form (`feat: release R4 - ...`), read the CI result for the LATEST commit (compare the run's head SHA with the PR head SHA) and squash-merge only when it is green. Do not run CI separately for each story.
7. CI as built: a pull request runs cheap checks plus only the tests the change can affect (about 3 to 13 minutes); the merge to main runs the DEPLOY GATE (all unit and integration tests in both time zones, build and size, and the 39 `@core` browser journeys on phone; keep `@core` between 30 and 45 and tag the new core flows); then `Deploy staging` runs automatically for the exact commit the gate tested and ends with a smoke test. Nightly runs the wide extras (desktop, WebKit, all colour modes, visual screenshots, Lighthouse) and publishes the `full-suite` status. Force a full run on a PR with the label or `[full-ci]` in the PR TITLE.
8. After every merge confirm the staging deploy is green and look at the live pages that changed. Run `node ai-tools/save-work.mjs` often (it snapshots every worktree and the tooling to GitHub).
